# 只只 · 人格系统与模型接入设计

> 定稿日期：2026-10-14　|　状态：🔒 **已与用户确认**
> 前置文档：《只只-架构设计与开发计划.md》（第四章 persona 扩展点）· 《电脑活起来-互动与情绪价值功能评估.md》（亲密度 trust）
> **本文档是 M5（台词池外置）的实现依据。**

## 〇、一句话结论

> ### 默认不接模型（纯台词池），但留一个极窄的口子；
> ### 而「换性格」要拆成四层 —— **换衣服，不换人。**

两条推论：

| | 结论 |
|---|---|
| **模型怎么接** | **内核里根本不该出现 `model` 这个概念。** 它落在 `persona` 插件里，走 **OpenAI 兼容协议**（一个 `fetch` 通吃本地与云端） |
| **性格能不能换** | ✅ 能换，但**宪法层不可换** —— 能让用户换性格，不能让它变成一个没分寸、乱传数据的东西 |

**用户原话（立为判据）**：

> **「这个只只是我们创造的，该保留的就应该保留。」**

## 一、问题拆成两个正交问题

用户原问：「配本地小模型，还是加个自定义配置模型的功能？」

**这其实是两个不同层的问题，混在一起就会掉进"要么内置一个模型、要么写一套 provider 适配层"的坑 —— 两个都不该做。**

| 问题 | 本质 | 结论 |
|---|---|---|
| **默认配不配本地模型？** | **默认值**问题 | ❌ **默认不配**。启动零依赖，装完就能跑 |
| **能不能自定义配置模型？** | **接口**问题 | ✅ **要留，但只留一个口子** |

---

## 二、关键省力发现：别抽象「模型」，复用「协议」

直觉做法是写一个 `ModelProvider` 接口，然后给 Ollama / OpenAI / DeepSeek / 通义各写一个适配器。**别这么干。**

几乎所有服务都实现了同一套协议 —— `/v1/chat/completions`：

| 本地 | 云端 |
|---|---|
| Ollama（`:11434`）· LM Studio（`:1234`）· vLLM · llama.cpp server | OpenAI · DeepSeek · 通义 · 智谱 · 各种中转站 |

> ### 一个 `fetch` 就全兼容了。用户想换模型，改一个 `baseUrl` 就行 —— **这不是"功能"，这是"没写代码"。**

这正是「不为还不存在的问题提前付成本」的反面示范：**真正的省力是发现标准已经存在，而不是自己造一个。**

**零配置的优雅路径**（以后做）：只只启动时探一下 `11434` / `1234` 端口，发现本地模型就冒一句：

> 「诶，你装了 Ollama。要我变聪明点吗？」—— **用户不填任何东西。**

---

## 三、⚠️ 只只独有的三条硬约束（别的 AI 应用没有）

**这是本文档最重要的一节。** 只只不是"又一个接大模型的应用"。

### ① 隐私：接云端 = 自我矛盾

只只的招牌是**安全哨兵**。如果它检测到「新增可疑自启项 `xxx.exe`，未签名」，然后把这条**发给云端 API** ——

> **为了安全，而泄密。**

**规则（宪法级）**：**安全类消息永远不走云端**，即使用户配了 API。

### ② 费用：成了新的沉默理由

沉默机制原本的理由是「不烦人」。加了付费 API 之后多一条：**不烧钱**。

**规则（宪法级）**：**绝不能让你月底收到一张账单。** 若配的是按量付费，只只必须比平时更克制。

### ③ 延迟：反而变成了人格的一部分

本地 2B 冷启动 1~3 秒。呼应我们早先定过的那句 —— **「它不是秒回，是在思考」**。

但**安全告警不能等模型** —— 所以回到分层：**告警走模板，聊天走模型。**

## 四、落点：`persona` 扩展点 —— 内核不需要知道「模型」存在

```
内核只认「一句台词」和「走哪个通道」
    ↑
    │  谁生产的台词，内核不关心
    │
persona 插件：
  ├─ 实现 A：静态 JSON 台词池      ← 默认，零依赖
  └─ 实现 B：调模型生成            ← 可选增强
```

> ### **内核里根本不该出现 `model` 这个概念。**

一旦内核知道"模型"存在，它就不再是纯粹的事件总线 + 调度器，而开始关心某个具体实现 —— **那是耦合的起点**（对应架构文档第三节：「人格不能交给插件」的反面，同样也**不该把实现细节塞进内核**）。

**顺带一次验证**：这件事能塞进 `persona` 而不用新增扩展点，说明 **6 类扩展点的划分是对的** —— `persona` 管**说什么**，`action` 管**做什么**，各司其职。

## 五、⭐ 人格四层：换衣服，不换人

**"支持换性格"如果做成"用户想换啥就换啥"，会出事。** 所以把人格拆成四层 —— 它们的**可换性不一样**：

| 层 | 内容 | 能换吗 | 为什么 |
|---|---|---|---|
| **宪法层** ⭐ | 沉默机制 · 不奉承 · 不催不说教 · **告警不走云端** · **性格包不许改阈值/行为** | ❌ **不可换** | 这是"只只还是只只"的判据 |
| **性格层** | 语气档位（毒舌 / 温柔 / 冷淡）、称呼、口头禅 | ✅ | 看腻的就是这层 |
| **台词层** | 每句话具体怎么说 | ✅ | 同上 |
| **形象层** | 名字、图标、配色 | ✅ | 最直观的新鲜感来源 |

### 打个比方

> **换的是衣服，不是人。** 你可以今天西装、明天卫衣，但你还是你。

### ⭐ 这条墙的**开源兜底**价值

> ### **别人做的性格包，再怎么烂，顶多是话不好听，不会变成一个疯狂弹通知骚扰你的东西。**

因为沉默机制是宪法，性格包碰都碰不到。**这是开源的兜底**：你开放了自定义，但把"行为危害"这条路**物理封死**了。同时它也保护了你 —— **别人改烂了，锅不是你的。**

### ⚠️ 一条硬规矩

**性格包不许改阈值。** 阈值是 `rule` 插件的事。**一旦性格包能让只只报得更勤，它就越界成插件了。**

## 六、新鲜感 vs 适配性（一个需求拆分）

用户观察：「人是有新鲜感的，看腻了。」

**观察对，但解法要换方向。** 真正让人腻的，不是"性格单一"，是"**它一成不变**"。

我们早先定的**亲密度系统（trust 0~100）**，本质上就是一套"性格随时间变化"的机制：

| 阶段 | 表现 |
|---|---|
| 陌生（0~39） | 冷淡、只报警、话少 |
| 熟悉（40~79） | 正常、偶尔主动搭话 |
| 亲近（80~100） | 话多、活泼、**开始吐槽你** |

> **这不是换了个性格，是同一个人跟你关系变深了。**
> **换性格包 = 换了个新玩具。亲密度 = 养出了一个关系。**

### 所以需求要拆成两个

| 实际遇到的 | 真正的解法 |
|---|---|
| 「**看腻了**」 | → **亲密度系统**（只只自己会变，不用你动手） |
| 「**这个性格不适合我**」（有人受不了毒舌） | → **性格包**（换性格的真实需求） |

**注意区别**：前者是**使用中**的问题，后者是**第一天**的选择问题。
→ **性格包的第一价值不是"换着玩"，是"让人选到合适的那个"。**

---

## 七、性格包规范：纯数据，不执行代码

如果以后想让它能被分享（"我这套性格写得不错，给你"），**这条现在定死**：

| | 性格包 |
|---|---|
| **形态** | **JSON + 可选图片**（纯数据） |
| **能做什么** | 改说什么、怎么说、什么口吻 |
| **不能做什么** | ❌ 执行代码 ❌ 改阈值 ❌ 改行为 |
| **分享成本** | 一个文件夹，拷过去就行 |
| **安全风险** | **零** |

想"加新能力"的，那是 `probe` / `rule` / `action` 插件的事 —— **两件事别混。**

---

## 八、三层接入，按这个顺序

| 层 | 形态 | 依赖 | 什么时候做 |
|---|---|---|---|
| **T0** | 纯台词池（模板 + 变量填充） | **无** | **M5 就做** —— 而且**它本身就是完整可用的产品** |
| **T1** | 本地模型（OpenAI 兼容，如 Ollama） | 用户自己的 Ollama | 之后加，约一个 `fetch` |
| **T2** | 云端 API（自己填 Key） | 用户自己的 Key | **同一套代码，改 `baseUrl`** |

> ### **T0 不是"阉割版"，T0 是正式版。**
> 我们早先算过 —— **90% 的话本来就该走台词池**。模型解决的是剩下那 10%：第一次见到的组合、以及你主动跟它聊天。

**M5 的关键动作**：把台词写成**外部 JSON 文件**，别写死在 TS 里。
——**就这一条，可替换性就有了。** 不需要配置文件、不需要切换 UI、不需要目录扫描。

## 九、落地形态

```
人格
 ├─ 宪法（内核写死，不可覆盖）⭐
 └─ persona 插件（可替换）
      ├─ 内置包：只只本尊（有人味 + 会吐槽）
      ├─ 自定义包：~/.zhizhi/personas/xxx.json   ← 用户 / 别人写的
      └─ 加载：现在静态读取（S2），以后扫目录（S3）
```

**时间窗口提醒**：

| 按"数据外置"写 | 成本 |
|---|---|
| **M5 写台词池时顺手做** | **≈ 0**（台词本来就要一句句写） |
| M5 之后再补 | 重构整个台词系统 |
| M6+ 才想起来 | 改内核 + 改所有插件 |

> **所以不是"留后路"，是"现在就是这条路"。**

### 📌 对 M5 验收标准的补充建议（待用户确认）

现标准：*改一个 JSON 字段，重启就能听到新台词* —— 已验证「数据外置」。

**建议补一条**：***把内置 persona 包改名/移走，用一份自写的最小 JSON 仍能跑起来*** —— 这才验证了「**可整体替换**」，而不只是「可微调」。

## 十、❌ 明确不做

| ❌ | 理由 |
|---|---|
| **在内核里做多模型适配层**（provider 抽象 / 配置校验 / 切换 UI） | 现在连一个模型都没有 —— **为不存在的问题付成本** |
| **内置捆绑一个模型** | 体积 +300MB~1GB，违背「占用小」的初衷，质量还差。只只应该是「**你有 Ollama 我就用，没有就纯台词池**」 |
| **性格编辑器 UI** | 想换的人改 JSON 完全够，爱折腾的不在乎这个（典型过度工程） |
| **性格市场 / 在线分发** | 已锁定「可自定义，不做平台」，这条不变 |
| **让性格包碰阈值和行为** | 越界 = 开了个后门 |

**该现在做的**：接口留窄口（`generate(prompt) → string`，走 OpenAI 协议）
**该以后做的**：配置 UI、端口自动探测、多 provider 切换

## 十一、本文档确立的新锁定决策

| # | 决策 | 层级 |
|---|---|---|
| **A** | 模型接入 = **默认不接**，留窄口，落 `persona` 插件，**内核不知道 `model` 存在** | 架构 |
| **B** | 模型协议统一走 **OpenAI 兼容**（`/v1/chat/completions`），不做 provider 适配层 | 架构 |
| **C** | 人格分四层，**宪法层不可换**（沉默 / 不奉承 / 不催不说教 / 告警不走云端 / 性格包不改阈值） | 宪法 ⭐ |
| **D** | **性格包 = 纯数据**（JSON + 图片），**不允许执行代码** | 安全 |
| **E** | 「安全类消息不走云端」「付费 API 下更克制」→ **并入沉默机制，宪法级** | 宪法 ⭐ |
| **F** | 新鲜感优先由**亲密度系统**承接；性格包解决的是「选到合适的那个」 | 设计取向 |

## 附：这次讨论为什么值得单独立档

因为**它决定了两件事的写法**，而这两件事一旦写错，返工成本很高：

1. **M5 台词池** —— 写成内联 TS，还是外部 JSON？
2. **M7 亲密度** —— 是"养成机制"，还是"性格切换的平替"？

而这两条的共同点是：**现在做几乎不花时间，以后补要重构。**

> 又一条贯穿全项目的原则：**定义格式很便宜，实现机制很贵。**

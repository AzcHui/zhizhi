## 一、结论先行

你的方向对，但**「一切皆插件」要改一个字**：

> ### ✅ 内核稳定 + **一切扩展点**皆插件
> ### ❌ 一切**皆**插件

三条判断：

| 你的主张 | 我的判断 | 一句话理由 |
|---|---|---|
| 先做能跑起来的骨架 | ✅ **完全赞同**，而且这是最重要的一步 | 骨架错了，后面全是返工 |
| 基础框架 / 一切皆插件 | ⚠️ **方向对，但必须先划边界** | 6 类该插件化，7 样绝**不能**插件化（第三节） |
| 后续开源让别人自定义 | ✅ 好目标 | 但**必须先锁定「可自定义」而不是「做平台」**（第二节） |

再加一条**时机建议**：

> **现在做「接口」（便宜），很久以后再实现「动态加载」（昂贵）。**
> 这两件事经常被绑在一起做 —— 那是整个决策里最贵的一次浪费。

## 二、先锁定战略前提：「可自定义」≠「做平台」

你说"开源了别人想怎么自定义自己决定"。这句话有两种读法，成本差 **10 倍**：

| | 🟢 A. 可自定义（**建议锁死**） | 🔴 B. 做平台（**建议放弃**） |
|---|---|---|
| 内容 | 改台词、改阈值、加采集器 / 规则 / 通道 | + 插件市场 + 版本管理 + 依赖解析 + 沙箱 + 审核 + 分发 |
| 面向谁 | 会改配置文件、会写 50 行 TS 的人 | 任何人 |
| 成本 | **低** | **另一个项目** |
| 长期负担 | 你只管内核 | 你要长期养生态 + 处理恶意插件投诉 |
| 你的定位 | 副业项目 + 自用工具 | 创业者 |

**为什么建议锁死 A？** 理由很实在：

1. 这个项目最迷人的部分是**「性格」**，而**性格恰恰是最不需要生态的部分**。你不需要 100 个插件，你需要的是 **6 个干净的扩展点 + 一份好写的文档**。
2. 搜到的实践资料里反复出现一条：**"You're early-stage and still finding the product shape"** 是「不该做插件系统」的头号理由。而你现在**正处在形状未定型的阶段** —— 所以正确的策略不是"不做扩展点"，而是**不把还不确定的东西提前抽象成接口**。
3. 插件市场是**运营问题**，不是技术问题。你的目标是"干活有趣 + 电脑安全"，不是"打造生态"。

> **一句话**：开源是为了**让别人能改**，不是为了**让别人来装**。差别就在于你要不要做分发和信任链。

## 三、为什么「一切皆插件」会翻车

这是整份文档最重要的一节。我查了 2026 年的插件架构实践，有一条几乎是共识：

> **"Plugins make change easier if the core stays disciplined.**
> **If the core leaks details everywhere, your plugin system becomes a high-tech way to spread chaos."**

翻成你的语境，这就是「一切皆插件」的典型翻车路径：

```
第 1 周：把「采样」「判断」「说话」全做成插件 → 感觉架构很干净 ✅
第 3 周：persona 插件想用 rule 插件的事件类型
        rule 插件想用 probe 插件的指标类型
        → 三个插件开始互相 import
第 5 周：改一个字段要改三个插件，"插件化"不但没解耦，
        反而多了一层间接、还更难调试
          ↓
     【分布式单体】——用插件的形式，写出了比原来更耦合的代码
```

### 正确的分界线：按「变化频率」划，不按「功能大小」划

| 判据 | ➡️ 进内核 | ➡️ 进插件 |
|---|---|---|
| **变化频率** | 几乎不变（事件总线十年不变） | 经常变（台词天天改、阈值天天调） |
| **是否每个部署都需要** | 需要（没它程序不成立） | 可选（可以没有） |
| **是否属于"品格"** | 是（沉默原则、分通道规则） | 不是 |
| **是否涉及安全边界** | 是（不能删文件、不能杀进程） | 不是 |

> ### 一句话：**内核是它的「人格与骨架」，插件是它的「感官与口才」。**

**人格不能交给插件** —— 否则你把"它是个什么样的东西"的决定权，交给了一个第三方脚本。这在一个**安全哨兵**定位的软件里，是致命的。

### 内核的 7 样东西（绝不插件化）

| # | 内核组件 | 为什么不能交出去 |
|---|---|---|
| 1 | **事件总线** | 它是插件之间的唯一通道。交出去 = 没人管秩序 |
| 2 | **调度器**（定时 / 条件触发） | 决定"什么时候该说话"，是分秒必争的控制权 |
| 3 | **状态存储**（事件日志 / 记忆 / 亲密度） | 它的"海马体"。插件能直接写 = 记忆可被污染 |
| 4 | **分通道规则** | 决定什么走浮窗、什么升级为 Toast。**这是它的分寸感** |
| 5 | **沉默机制**（冷却 / 静默时段 / 降噪） | ⭐ **最重要的一个**。这是"活"的最高级形态，绝不能允许插件绕过 |
| 6 | **权限裁决** | 插件能做什么，由内核说了算（第九节） |
| 7 | **插件加载器** | 引导程序。能被插件替换 = 自举失控 |

**第 5 条我要单独强调**：

> 在《互动与情绪价值评估》里我们定过一句话 —— **「一直叫的不像活的，像闹钟。有分寸才像活的。」**
> 如果插件能绕过冷却期、能无视静默时段，那么"分寸"就不再是**内核的品格**，而变成了**某个插件的自觉**。
> 而这东西能不能长期开着，**完全取决于它有没有分寸**。
>
> **所以：沉默机制是内核的宪法，不是插件的配置项。**

### ⭐ 沉默机制的宪法条款（2026-10-14 扩充）

「沉默机制」不只是冷却期和静默时段 —— 它是**一组不允许任何插件推翻的底线规则**。目前已确立 **5 条**：

| # | 条款 | 为什么是宪法 |
|---|---|---|
| 1 | **冷却期 / 静默时段 / 降噪** | 分寸感。绕过它 = 从"活物"退化成"闹钟" |
| 2 | **每天主动说话有上限**，超了只记日志 | 通知疲劳是这东西最可能的死因 |
| 3 | 🆕 **安全类消息不走云端** | 只只是安全哨兵 —— 把「检测到可疑自启项」发给云端 = **为了安全而泄密**（自我矛盾） |
| 4 | 🆕 **付费模型下必须更克制** | 沉默多了一条理由：**不烧钱**。绝不能让你月底收到一张账单 |
| 5 | 🆕 **性格包不许改阈值 / 行为** | 能改「怎么说」，不能改「多频繁」「做什么」。越界 = 后门 |

> **条款 5 是开源的兜底**：有了它，**别人做的烂性格包，顶多是话不好听，不会变成一个疯狂弹窗骚扰你的东西**。
> 详见《只只-人格系统与模型接入设计.md》第五节。

## 四、六类扩展点（骨架的核心）

这六个是**全部**的插件接口。不多不少 —— 每多一个，你就多一份长期维护成本。

| # | 扩展点 | 插件提供什么 | 官方首发示例 | 社区能改什么 |
|---|---|---|---|---|
| **1** | **probe**（采集器） | 产生**指标**（指标是数据，不是文字） | `probe-cpu` `probe-mem` `probe-disk` `probe-proc` `probe-net` | 加显卡、温度、电池、外设、自定义指标 |
| **2** | **rule**（判断规则） | 消费指标 → 产生**事件** | `rule-threshold` `rule-sustained` `rule-baseline` `rule-sentinel`(安全基线) | 加自己的判断逻辑（如"编译期间静音"） |
| **3** | **persona**（台词包） | 事件 + 情境 → **台词**（**纯数据，不是代码**） | `persona-zhi`（只只的语气） | ⭐ **最容易改的一层**：改 JSON 就换性格 |
| **4** | **channel**（通道） | 把一句话**送去哪儿** | `channel-bubble`（浮窗气泡）`channel-toast` `channel-tray` | 加声音、加手机推送、加终端输出 |
| **5** | **action**（动作） | 用户点击后**做什么** | `action-open-taskmgr` | 加自己的快捷操作（**高危，需权限声明**） |
| **6** | **view**（面板） | 额外 UI 页面 | `view-status` `view-history` | 加自定义面板（**最难，最后做**） |

### ⭐ 为什么 `persona`（台词包）是最关键的一层

因为它**是"别人想怎么自定义自己决定"这个诉求的最低成本实现**：

```
改台词：改一个 JSON 文件       → 零编程基础，重启即生效
改判断：写 20 行 TS           → 会写前端的人都能干
改采集：写 50 行 TS           → 需要一点系统知识
改面板：写一个 Vue 组件       → 收益最低、成本最高
```

**所以开源时，你的 README 第一句话应该是「想让它换个性格？改 `persona-zhi/persona.json`就行」** —— 这会决定你的项目是"有人会去改"还是"star 完就走"。

> ### 📎 展开详见《只只-人格系统与模型接入设计.md》
> `persona` 这一层的完整设计（**人格四层 · 宪政层不可换 · 性格包纯数据规范 · 模型接入三层 T0/T1/T2 · 内核不知道 `model` 存在**）已单独立档 —— 它是 **M5 台词池外置的实现依据**。

### ⚠️ 三条不可谈判的插件规则

| 规则 | 说明 | 违反的后果 |
|---|---|---|
| **① 插件之间禁止互相 import** | 只能通过**内核事件总线**通信；跨插件的数据结构**定义在内核里**（不是插件里） | N² 耦合 → 分布式单体 |
| **② 第一方插件必须走同一套接口** | 官方内置的 `probe-cpu` 也不许有"内核特权" | 接口设计会因"反正内核能绕过"而变烂 |
| **③ 插件崩溃不许带崩内核** | 每个插件初始化独立 try/catch + 状态机（`discovered → active → failed`） | 一个坏插件 = 整个软件哑巴 |

**第 ② 条（dogfooding）是最容易偷懒的一条，也是最贵的一条。** 很多项目的插件系统烂掉，就是因为第一方走了后门 —— 于是接口从来没被真正使用过，等第三方来用才发现根本不好用。

## 五、⚠️ 两层插件千万别混（一个容易踩的坑）

Tauri 自己有一套插件系统（`tauri-plugin-*`）。**它和我们要做的「应用插件」是两码事，混在一起会灾难。**

| | **Tauri 官方插件层** | **只只的应用插件层**（本项目） |
|---|---|---|
| 语言 | **Rust**（crate） | **TypeScript** |
| 装什么 | 系统能力：`fs` / `shell` / `notification` / `dialog` | 业务扩展：probe / rule / persona / channel |
| 谁写 | **只有你（维护者）** | 社区 |
| 贡献门槛 | 装 Rust 工具链 + 编译整个应用 | 复制一个文件夹，改 20 行 TS |
| 加载时机 | **编译期**（打进二进制） | 运行期（未来） |
| 权限模型 | `capabilities/*.json`，默认全禁 | 内核自己的 manifest，默认全禁 |

> ### 结论：**Tauri 插件只用来做系统能力，由你独家管理；社区扩展一律走 TS 应用插件层。**

**为什么不把社区插件做成 Tauri Rust 插件？** 三个理由，任何一个都足够：

1. **门槛太高**：要装 Rust（~5GB）+ MSVC Build Tools，还要 `cargo build` 整个应用 —— 会把 99% 的潜在贡献者挡在门外
2. **编译期加载**：改一行台词要重新编译整个 Rust 应用，等于没有"自定义"
3. **安全模型不同**：Rust 插件有进程内完整权限，社区插件必须是受限的

⚠️ **唯一的例外**：如果某个社区扩展**必须**深度调用 Windows API（比如读温度传感器），那它只能作为 Tauri 插件由**你审核后合并**，不能开放给社区自由提交。这是个**审核流程**问题，不是技术问题。

```

│   │   ├── scheduler.ts         调度器（定时 / 条件触发）

│   │   └── channel-bubble/
│   │
│   ├── cli/                     ⭐ 内核独立运行入口（M0 就能跑，不需要 Tauri）
│   │   └── main.ts              采样 → 判断 → 打印/写日志
│   │
│   └── app/                     Tauri 外壳（Vue3）—— 最后一层
│       ├── src/                 Vue 页面（浮窗、气泡、设置）
│       └── src-tauri/           Rust 侧：窗口样式 + sidecar 启动
│
└── docs/
    ├── plugin-guide.md          ⭐ 写给未来贡献者的（决定项目生死）
    └── examples/                三个最小插件示例
```

### ⭐ 这个结构里最重要的一条约束

> ### `packages/core` 必须**零 UI 依赖**，能被 `cli` 和 `app` 同时消费。

因为这一条**物理上保证**了「先内核后外壳」不是一句口号：

```
     ┌──────────────┐
     │  core 内核   │  ← 零 UI 依赖，能独立 npm run
     └──────┬───────┘
            │  同一个内核，两个消费者
     ┌──────┴───────┐
     ▼              ▼
  ┌──────┐      ┌──────────┐
  │ cli  │      │ app(Tauri)│  ← 只是"脸"，可替换
  └──────┘      └──────────┘
  今天就用        以后再建
```

**它带来三个白捡的收益**：

1. **M0 阶段零成本验证**：内核能独立跑，控制台就能看结果，**完全不需要先装 Rust**
2. **外壳可以换**：今天选 Tauri，将来想换 Electron 甚至 Web，内核一行不改
3. **开源时多一种用法**：有人只想要内核（接自己的界面 / 接自己的通知），不要你的 GUI

## 七、内核 ↔ 外壳 怎么连（技术方案）

Tauri 官方支持把 Node 进程作为 **sidecar** 常驻，通过 stdio 通信。核实到的**三个关键坑**（都会让人卡半天）：

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | 一次性命令 ≠ 常驻进程 | `.output()` 是一次性的；**常驻必须用 `.spawn()`**，它返回 `(Receiver, CommandChild)` |
| 2 | **CommandChild 会随 drop 被杀** | **必须一直持有它**（存到 app state），否则子进程莫名退出 |
| 3 | `setup()` 是同步的、没有 tokio reactor | 在里面 spawn 要用 `tauri::async_runtime::block_on(...)`，后台任务用 `tauri::async_runtime::spawn`（**不是** `tokio::spawn`） |

配套：`tauri.conf.json` 里配 `bundle.externalBin`，二进制要带 target triple 后缀（如 `zhizhi-core-x86_64-pc-windows-msvc.exe`）。

### 📌 MVP 阶段不做打包

**别一上来就折腾 sidecar 打包**（`pkg` / `bun build --compile` / Node SEA）。理由：

- **多进程 + IPC 序列化开销**：对"5 秒采样一次"的场景**完全无所谓**，不是瓶颈
- MVP 阶段直接 `spawn` 系统 Node 跑 TS 源码就行（你有 nvm4w 的 Node v22.22.2）
- **打包是"发布"该做的事，不是"开发"该做的事**（又一次：别提前支付成本）

### 协议：一行一个 JSON（line-delimited JSON over stdio）

```
内核 → 外壳：  {"type":"event","level":"warn","text":"内存有点挤…"}
外壳 → 内核：  {"type":"feedback","eventId":"e_1042","vote":"down","reason":"too_frequent"}
```

**极简、可调试**（肉眼能看 stdout）、**零依赖**。别上 gRPC / WebSocket —— 那是过度工程化。

## 八、⭐ 渐进式落地：接口现在做，加载器以后做

**这是整份文档最能省钱的一条建议。**

| 阶段 | 做什么 | 成本 | 什么时候 |
|---|---|---|---|
| **S1 契约先行** | 定义 TS 接口 + manifest 规范；插件**静态 import**（Vite 打包进来） | **极低** | ⭐ **现在** |
| **S2 数据外置** | 台词池 / 阈值配置移到本地 JSON，用户可改 | 低 | 开源前 |
| **S3 动态加载** | 扫描 `pluginsDir` + 动态 `import()` + 权限校验 | 中 | **真有第三方需求时** |
| **S4 沙箱隔离** | worker_threads / WASM 隔离 | **高** | 真有人提交崩溃/恶意插件时 |

```
成本
 ▲
 │                                        ┌──── S4 沙箱（代价最高）
 │                                        │
 │                             ┌──────────┘
 │                    ┌──────── S3 动态加载
 │           ┌────────┘
 │  ┌────────┘ S2 数据外置
 │──┘ S1 契约先行  ← 你只需要走到这里，就能拿到插件化的绝大部分好处
 └────────────────────────────────────────▶ 时间/需求
```

### 为什么 S1 就够用了

| S1（静态注册） | S3（动态加载） |
|---|---|
| 编译期**类型检查** | 运行期才发现接口错了 |
| **更快**（无运行期 import） | 每次启动要扫目录、解析、校验 |
| 崩溃**编译时**就发现 | 崩溃在用户机器上 |
| 缺点：加插件要重新 build | 优点：扔进文件夹就能用 |

> **关键认知：定义接口很便宜，实现加载器很贵。**
> 而接口的收益（解耦、可替换、可读）**从第一天就兑现**，加载器的收益（第三方免编译安装）**要等真的有人来写插件才兑现**。

**所以 S3 应该被"需求"触发，而不是被"规划"触发。**

## 九、安全模型（这个项目独有的、必须做的一环）

这里有个**讽刺但绕不过去**的点：

> **只只本身是"安全哨兵"。如果它加载第三方插件时没有权限模型，那用户为了「更安全」而装插件，结果引入了整台机器上最大的攻击面。**

**这不是可选项，是这个项目定位的必然要求。**

### manifest 权限声明（默认全禁）

```jsonc
// plugins/probe-temp/manifest.json
{
  "id": "probe-temp",
  "name": "温度采集",
  "version": "0.1.0",
  "type": "probe",
  "sdk": "^0.1.0",              // 兼容的 SDK 版本（语义化）
  "permissions": {
    "fs":  [],                   // 不许读文件（默认空）
    "net": [],                   // 不许联网（默认空）
    "exec": [],                  // 不许执行命令（默认空）
    "sys": ["hardware.read"]     // 只申请它需要的那一项
  },
  "entry": "./index.ts"
}
```

**设计原则直接借鉴 Tauri v2 的 capability 模型**（搜到资料原文）：**"前端默认不能调用任何插件命令，必须在 capabilities 文件里显式声明权限。"** 这是被验证过的、正确的最小权限模型。

### ⚠️ 但要诚实：**MVP 阶段没有真沙箱**

| 隔离方式 | 强度 | 成本 | 什么时候用 |
|---|---|---|---|
| 同进程 + 权限包装 | **弱**（能防手滑，防不了恶意） | 极低 | ⭐ MVP |
| `worker_threads` | 中（防崩溃、防阻塞） | 中 | S3 |
| `child_process` / WASM | 强 | 高 | S4 |

**明确的态度**：

> **MVP 阶段对外说清楚「只加载你信任的插件」**，不要假装有沙箱。
> 沙箱是为"陌生人的代码"准备的 —— 而在 S1/S2 阶段，插件**全是你自己写的**，根本不存在陌生代码。
>
> **又一次：不要为还不存在的问题提前支付成本。**

## 十、外壳选型：⭐ 建议推迟到 M4

因为内核独立（第六节），**外壳是可替换的**，所以这个选择不必现在做。但对比先给你：

| | **Tauri 2 + Node sidecar**（前文建议） | **Electron**（省事选项） |
|---|---|---|
| 内存 | **30~50 MB** ⭐ | 150~300 MB |
| 前置 | 装 Rust（~5GB）+ MSVC Build Tools | **零**（你有 Node） |
| 内核接入 | sidecar + stdio IPC（三层：Vue↔Rust↔Node） | **直接 import 内核**（零 IPC）⭐ |
| 渲染 | 系统 WebView（Win11 上是 WebView2） | 自带 Chromium（体积大但一致） |
| 透明浮窗 | 要自己调 `WS_EX_NOACTIVATE`（`windows` crate） | 原生支持 `setIgnoreMouseEvents` / `focusable:false` |
| 你的技术栈匹配度 | Vue3 ✅（Rust 部分要学） | **Vue3 ✅ + Node ✅（全是你熟的）** |

**我的建议**：

> **先只用 `cli` 把内核做到 M3（含 P0-b 手感验证），再决定要不要上 Tauri。**
>
> 如果到那时你**仍然在意那 150MB 内存差** → Tauri；如果觉得**"少一个 Rust 工具链 + 少一层 IPC"更值得** → Electron，完全不丢人。
>
> ⭐ **这就是"内核独立"带来的最大收益：把最贵的选型决策，推迟到信息最充分的时候。**

## 十二、明确不做

| ❌ 不做 | 理由 |
|---|---|
| **插件市场 / 分发 / 审核** | 从"可自定义"升级成"做平台"，是另一个项目（第二节） |
| **插件依赖解析** | 那是 npm 的活，别重造。真要依赖，让插件自己声明 npm 依赖 |
| **让插件 hook 内核的关键节点** | ⭐ **"一切皆插件"最经典的翻车点** —— 内核交出控制权 = 失去纪律 |
| **MVP 阶段的真沙箱** | 插件都是你自己写的，没有"陌生代码"问题（第九节） |
| **Tauri Rust 插件开放给社区** | 门槛 + 编译期加载 + 权限过宽，三个硬伤（第五节） |
| **一上来做 `view`（UI 插件）** | 收益最低、成本最高（Vite 运行期加载 Vue 组件还要处理 CSP），永远放最后 |
| **提前折腾 sidecar 打包** | 发布阶段的事，不是开发阶段的事（第七节） |

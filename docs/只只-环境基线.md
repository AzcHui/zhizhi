### ⚠️ 最重要的一条：`node_modules` 里的 `.ts` 跑不了

Node 的原文报错：

```
Error [ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING]:
Stripping types is currently unsupported for files under node_modules,
for "D:\MyProjects\zhizhi\node_modules\__ts_probe\lib.ts"
```

**那 pnpm workspace 的插件为什么能跑？** —— 因为**软链被 realpath 展开了**：

```
import.meta.resolve('@zhizhi/probe-cpu')
  → file:///D:/MyProjects/zhizhi/packages/plugins/probe-cpu/src/index.ts   ← 真实路径，不在 node_modules 下
```

磁盘上它确实是个软链：

```
packages/cli/node_modules/@zhizhi/probe-cpu
  -> /d/MyProjects/zhizhi/packages/plugins/probe-cpu
```

Node 默认 `preserveSymlinks=false`，解析模块时把软链展开成真实路径，于是**绕开了** `node_modules` 限制。

> ⚠️ 这是「**恰好能跑**」，不是「设计如此」—— 所以下面那条推论必须记住。

## 四、这个发现对架构的直接影响 ⭐

| # | 结论 | 影响 |
|---|---|---|
| 1 | **插件不能是「真装在 `node_modules` 里的 `.ts` 包」** | 一旦从 npm 装进 `node_modules`，`.ts` 直接炸 |
| 2 | **S3 动态加载的形态被限定了** | 只能「扫 `pluginsDir` 目录 + 按路径 `import()`」，**不能是「npm install 一个插件包」** |
| 3 | 若将来要把插件发到 npm | 必须是**编译后的 `.js`**（或以整个目录分发），不能发 `.ts` |
| 4 | 我们自己的 workspace 插件没事 | 软链 → realpath 落在项目内，实测可加载 |
| 5 | 项目对 Node 版本有硬要求 | `>=22.18`（type stripping 默认开启的版本）。Node 20 用户跑不起来 —— **M9 开源时 README 必须写明** |

> 换个说法：**我们享受了「零构建」的好处，代价是「插件分发形态受限」。**
> 这笔账要在 M9（开源准备）时对外讲清楚，别让贡献者踩坑。

### ⭐⭐⭐ 画字变红叉：**已挂到控件上的字体不能 Dispose**（M3 二次踩坑）

M3 浮窗第二次事故：窗口一打开，**满屏红叉**（每个控件一个）。`tools/float-preview.log` 里是：

```
[ERR] Application.ThreadException（全局兜底） -> System.ArgumentException | 参数无效。
   .net : System.Drawing.Graphics.CheckErrorStatus(Int32 status)
          System.Drawing.Graphics.DrawString(...)
          System.Windows.Forms.Label.OnPaint(PaintEventArgs e)
   ……同理 Button 走的是 MeasureString
```

**11 条 = 6 个标签 + 5 个按钮，每个控件恰好失败一次** —— WinForms 会把「绘制时抛异常的控件」画成红叉。

| 要点 | 说明 |
|---|---|
| **真凶** | `Set-Layout` 里那句「先 `Dispose()` 旧字体，再新建赋值」。控件此刻仍指向**已释放的 Font** → GDI+ 下一次画字（`DrawString` / `MeasureString`）抛 `ArgumentException: 参数无效` → 控件被画成红叉 |
| ⚠️ **为什么极难复现** | 字体 GDI+ 句柄**带引用计数**：句柄还被别处持有时没事，恰好归零才炸 → **同一份代码时好时坏**（实测：16:15 通过，16:1x 连续 11 错）。我因此**误判过两次**（先怪 `Form.TopMost`、再怪 `Add-Type`） |
| ⭐ **定位方法** | 写一个**能自我截屏**的探针（`Graphics.CopyFromScreen` 存 PNG → 肉眼比对），再做**单变量二分**。最后两个命中项：`不销毁字体` → 0 错；`改用 GDI 文字渲染` → 0 错 |
| ✅ **正解** | **按尺寸缓存字体、进程内永不 `Dispose`**（最多 9 个 Font，可忽略）→ `Get-FontSet 'md'` |
| 🧪 **防止再犯** | 新增 `-RenderCheck`：真开窗 ~0.9s → 数「绘制期异常」→ 存截图 → 退出。**动过渲染相关代码就跑一次** |

> ⚠️ 两条纪律：
> ① **`-SelfTest` 不弹窗 = 不绘制，因此抓不到绘制类缺陷** —— 红叉正是这么漏过去的，所以才补了 `-RenderCheck`。
> ② **别拿「同一份代码侥幸通过一次」当结论**；引用计数型的缺陷必须看多次结果。

### ⭐⭐ 最要紧的一条：WinForms 脚本的「异常兜底」与「管道停止」

M3 浮窗实跑时炸过一次：弹 .NET 致命对话框，异常文本
`System.Management.Automation.PipelineStoppedException: 管道已被停止。`，控制台再没回到提示符。
四个探针把可疑点逐个排掉后，结论如下 —— **全部本机实测**：

| 我怀疑的 | 实测结果 |
|---|---|
| 事件处理器里 `Write-Host` | ✅ 不抛 |
| 事件处理器里调 cmdlet / `New-Object` | ✅ 不抛 |
| Paint 重入（处理器里 `$form.Refresh()`） | ✅ 不抛 |
| 嵌套委托调用（A 的处理器里 `$btnB.PerformClick()`） | ✅ 不抛 |
| 处理器里**抛错**会怎样 | ❌ **直接冒到消息循环 → .NET 致命对话框**；不点「继续」就永远卡住 |
| `SetUnhandledExceptionMode(CatchException)` + `Application::add_ThreadException(脚本块)` | ✅ 可用且**有效**：实测弹窗被我们自己的处理器替换掉，程序继续运行 |

**`PipelineStoppedException` 的成因不是「代码写法」，而是「管道真的被停掉了」**：

| 要点 | 说明 |
|---|---|
| 触发 | 在跑着 WinForms 的控制台里按 **Ctrl+C** —— 脚本正阻塞在 `ShowDialog()`，PS 会先把管道标记为停止 |
| 后果 | 此后**任何**事件处理器调用都会在 `ScriptBlock.InvokeWithPipeImpl` 直接抛 `PipelineStoppedException`，**连 `try/catch` 都进不去**（异常发生在「进入脚本块」之前） |
| 表象 | 弹 .NET 致命对话框 **+** 控制台再也不返回提示符（两条症状同时出现） |
| 对策 | ① **别在控制台按 Ctrl+C**，关窗点 ✕ ② 处理器里**一律不往控制台写**，只写日志文件（控制台若处于「快速编辑/选中」状态，写入会被阻塞） ③ 每个处理器自带 `try/catch` ④ 再加一层全局兜底（上表最后一行） |

> 纪律（由此推导）：**GUI 脚本必须自带异常兜底**。
> PowerShell 里裸的事件处理器没有「未捕获异常」的缓冲 —— 一次异常 = 一次致命弹窗。
> 另：**别用 `SendMessage(WM_NCLBUTTONDOWN)` 借系统标题栏拖窗口**，它会在处理器内部再开一个
> 模态消息循环（等于在委托里再抽一次消息），是处理器重入的高风险点；改成「记偏移 + 设置 Location」即可。

### ⚠️ 置顶开关：别手打 `WS_EX_TOPMOST` 位

实测（本机，窗口**尚未显示**时）：

| 做法 | 结果 |
|---|---|
| `SetWindowLong(EXSTYLE \| 0x8)` | ❌ **不稳** —— OR 进去后读回又没了 |

### ⭐ 最要紧的一条：`.ps1` 的编码 —— 加 BOM 就能写中文

**PS 5.1 读 `.ps1` 的规则**（实测：两个文件同样内容，只差 BOM）：

```
UTF-8 带 BOM    → 只只        ✅ 正确
UTF-8 不带 BOM  → 鍙彧        ❌ 按 GBK 解码 → 乱码
```

| 结论 | 说明 |
|---|---|
| ✅ **`.ps1` 可以写中文** | 前提是**存成 UTF-8 with BOM**。旧说法「脚本一律纯 ASCII」过于保守 —— 那是**没有 BOM 时**的兜底 |
| ⚠️ 本项目的 Write / Edit 工具**不写 BOM** | 所以每次改完 `.ps1` 要**重新补 BOM**，否则下次运行中文全乱 |
| ✅ 补 BOM 的办法 | `[System.IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding($true)))` |

### 复核命令

```powershell
# BOM 是否为 EF BB BF
$p='tools\float-preview.ps1'; ([System.IO.File]::ReadAllBytes($p)[0..2] | ForEach-Object { '{0:X2}' -f $_ }) -join ' '

$base = 'D:\MyProjects\zhizhi'; $nm = "$base\packages\cli\node_modules\@zhizhi"
New-Item -ItemType Directory -Force -Path $nm | Out-Null
Get-ChildItem "$base\packages\plugins" -Directory | ForEach-Object {

```

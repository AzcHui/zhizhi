### ⚠️ 最重要的一条：`node_modules` 里的 `.ts` 跑不了

Node 的原文报错：

```
Error [ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING]:
Stripping types is currently unsupported for files under node_modules,
for "D:\MyProjects\zhizhi\node_modules\__ts_probe\lib.ts"
```

**那 pnpm workspace 的插件为什么能跑？** —— 因为**软链被 realpath 展开了**：

```
import.meta.resolve('@zhizhi/probe-cpu')
  → file:///D:/MyProjects/zhizhi/packages/plugins/probe-cpu/src/index.ts   ← 真实路径，不在 node_modules 下
```

磁盘上它确实是个软链：

```
packages/cli/node_modules/@zhizhi/probe-cpu
  -> /d/MyProjects/zhizhi/packages/plugins/probe-cpu
```

Node 默认 `preserveSymlinks=false`，解析模块时把软链展开成真实路径，于是**绕开了** `node_modules` 限制。

> ⚠️ 这是「**恰好能跑**」，不是「设计如此」—— 所以下面那条推论必须记住。

## 四、这个发现对架构的直接影响 ⭐

| # | 结论 | 影响 |
|---|---|---|
| 1 | **插件不能是「真装在 `node_modules` 里的 `.ts` 包」** | 一旦从 npm 装进 `node_modules`，`.ts` 直接炸 |
| 2 | **S3 动态加载的形态被限定了** | 只能「扫 `pluginsDir` 目录 + 按路径 `import()`」，**不能是「npm install 一个插件包」** |
| 3 | 若将来要把插件发到 npm | 必须是**编译后的 `.js`**（或以整个目录分发），不能发 `.ts` |
| 4 | 我们自己的 workspace 插件没事 | 软链 → realpath 落在项目内，实测可加载 |
| 5 | 项目对 Node 版本有硬要求 | `>=22.18`（type stripping 默认开启的版本）。Node 20 用户跑不起来 —— **M9 开源时 README 必须写明** |

> 换个说法：**我们享受了「零构建」的好处，代价是「插件分发形态受限」。**
> 这笔账要在 M9（开源准备）时对外讲清楚，别让贡献者踩坑。

### ⭐⭐⭐ 画字变红叉：**已挂到控件上的字体不能 Dispose**（M3 二次踩坑）

M3 浮窗第二次事故：窗口一打开，**满屏红叉**（每个控件一个）。`tools/float-preview.log` 里是：

```
[ERR] Application.ThreadException（全局兜底） -> System.ArgumentException | 参数无效。
   .net : System.Drawing.Graphics.CheckErrorStatus(Int32 status)
          System.Drawing.Graphics.DrawString(...)
          System.Windows.Forms.Label.OnPaint(PaintEventArgs e)
   ……同理 Button 走的是 MeasureString
```

**11 条 = 6 个标签 + 5 个按钮，每个控件恰好失败一次** —— WinForms 会把「绘制时抛异常的控件」画成红叉。

| 要点 | 说明 |
|---|---|
| **真凶** | `Set-Layout` 里那句「先 `Dispose()` 旧字体，再新建赋值」。控件此刻仍指向**已释放的 Font** → GDI+ 下一次画字（`DrawString` / `MeasureString`）抛 `ArgumentException: 参数无效` → 控件被画成红叉 |
| ⚠️ **为什么极难复现** | 字体 GDI+ 句柄**带引用计数**：句柄还被别处持有时没事，恰好归零才炸 → **同一份代码时好时坏**（实测：16:15 通过，16:1x 连续 11 错）。我因此**误判过两次**（先怪 `Form.TopMost`、再怪 `Add-Type`） |
| ⭐ **定位方法** | 写一个**能自我截屏**的探针（`Graphics.CopyFromScreen` 存 PNG → 肉眼比对），再做**单变量二分**。最后两个命中项：`不销毁字体` → 0 错；`改用 GDI 文字渲染` → 0 错 |
| ✅ **正解** | **按尺寸缓存字体、进程内永不 `Dispose`**（最多 9 个 Font，可忽略）→ `Get-FontSet 'md'` |
| 🧪 **防止再犯** | 新增 `-RenderCheck`：真开窗 ~0.9s → 数「绘制期异常」→ 存截图 → 退出。**动过渲染相关代码就跑一次** |

> ⚠️ 两条纪律：
> ① **`-SelfTest` 不弹窗 = 不绘制，因此抓不到绘制类缺陷** —— 红叉正是这么漏过去的，所以才补了 `-RenderCheck`。
> ② **别拿「同一份代码侥幸通过一次」当结论**；引用计数型的缺陷必须看多次结果。

### ⭐⭐ 读子进程的输出：**绝不用 `add_OutputDataReceived`**

M4-a 要让浮窗**实时**显示内核的数据 —— 于是要**长连接读一个 node 子进程的 stdout**。实测结论：

| 做法 | 结果 |
|---|---|
| `$proc.add_OutputDataReceived({...})` | ❌ **不要用**。那个回调跑在**线程池线程**上，PowerShell 的脚本块在那种线程上会炸（没有 Runspace / 管道已停止）—— 与上面 ⭐⭐ 条同源 |
| **UI 线程「轮询异步读」** | ✅ **正解**：每次只挂一个 `$reader.ReadLineAsync()`，由 WinForms Timer（或主循环）检查 `.IsCompleted` → 取 `.Result` → 再挂下一个。**零线程、零阻塞** |

实测（探针，子进程 `--interval=800 --ticks=5`）：轮询 42 次 → **收到 5 条 stdout + 3 条 stderr**，
解析出 `tick=1 cpu=23.6% mem=61.3%` —— 确认拿到的是**持续流**，不是一次性。

两条附加约束：

| # | 约束 | 为什么 |
|---|---|---|
| 1 | **必须显式设** `StandardOutputEncoding` / `StandardErrorEncoding = UTF8`（且在 `RedirectStandard*=true` **之后**设） | 不设的话 PowerShell 按 **GBK** 解码子进程输出 → **只只说的中文全变乱码**（探针实测踩到） |
| 2 | **stderr 也必须一直抽干** | 管道缓冲区（约 64KB）写满后，**子进程会被阻塞**。顺带的好处：只只说的话就在 stderr 里 |

```powershell
# 复制即用：起一个常驻子进程并持续读它两路输出
$psi = New-Object System.Diagnostics.ProcessStartInfo
$psi.FileName = 'node'; $psi.Arguments = '…'; $psi.UseShellExecute = $false
$psi.RedirectStandardOutput = $true; $psi.RedirectStandardError = $true
$psi.StandardOutputEncoding = New-Object System.Text.UTF8Encoding($false)   # ⚠️ 必须
$psi.StandardErrorEncoding  = New-Object System.Text.UTF8Encoding($false)   # ⚠️ 必须
$proc = [System.Diagnostics.Process]::Start($psi)
$outTask = $proc.StandardOutput.ReadLineAsync()   # 只挂一个，「完成了吗」交给 UI 线程问
$errTask = $proc.StandardError.ReadLineAsync()
```

> 📌 回收：**关窗时一定要 `Kill()` 子进程**，否则会在后台留一个孤儿 node（M4-a 是在 `FormClosing` 里收的）。
> 窗口被**强杀**时 `FormClosing` 不跑 —— 那种情况下靠子进程往断管写数据自行退出，但不保证。

### ⭐⭐ 最要紧的一条：WinForms 脚本的「异常兜底」与「管道停止」

M3 浮窗实跑时炸过一次：弹 .NET 致命对话框，异常文本
`System.Management.Automation.PipelineStoppedException: 管道已被停止。`，控制台再没回到提示符。
四个探针把可疑点逐个排掉后，结论如下 —— **全部本机实测**：

| 我怀疑的 | 实测结果 |
|---|---|
| 事件处理器里 `Write-Host` | ✅ 不抛 |
| 事件处理器里调 cmdlet / `New-Object` | ✅ 不抛 |
| Paint 重入（处理器里 `$form.Refresh()`） | ✅ 不抛 |
| 嵌套委托调用（A 的处理器里 `$btnB.PerformClick()`） | ✅ 不抛 |
| 处理器里**抛错**会怎样 | ❌ **直接冒到消息循环 → .NET 致命对话框**；不点「继续」就永远卡住 |
| `SetUnhandledExceptionMode(CatchException)` + `Application::add_ThreadException(脚本块)` | ✅ 可用且**有效**：实测弹窗被我们自己的处理器替换掉，程序继续运行 |

**`PipelineStoppedException` 的成因不是「代码写法」，而是「管道真的被停掉了」**：

| 要点 | 说明 |
|---|---|
| 触发 | 在跑着 WinForms 的控制台里按 **Ctrl+C** —— 脚本正阻塞在 `ShowDialog()`，PS 会先把管道标记为停止 |
| 后果 | 此后**任何**事件处理器调用都会在 `ScriptBlock.InvokeWithPipeImpl` 直接抛 `PipelineStoppedException`，**连 `try/catch` 都进不去**（异常发生在「进入脚本块」之前） |
| 表象 | 弹 .NET 致命对话框 **+** 控制台再也不返回提示符（两条症状同时出现） |
| 对策 | ① **别在控制台按 Ctrl+C**，关窗点 ✕ ② 处理器里**一律不往控制台写**，只写日志文件（控制台若处于「快速编辑/选中」状态，写入会被阻塞） ③ 每个处理器自带 `try/catch` ④ 再加一层全局兜底（上表最后一行） |

> 纪律（由此推导）：**GUI 脚本必须自带异常兜底**。
> PowerShell 里裸的事件处理器没有「未捕获异常」的缓冲 —— 一次异常 = 一次致命弹窗。
> 另：**别用 `SendMessage(WM_NCLBUTTONDOWN)` 借系统标题栏拖窗口**，它会在处理器内部再开一个
> 模态消息循环（等于在委托里再抽一次消息），是处理器重入的高风险点；改成「记偏移 + 设置 Location」即可。

### ⚠️ 置顶开关：别手打 `WS_EX_TOPMOST` 位

实测（本机，窗口**尚未显示**时）：

| 做法 | 结果 |
|---|---|
| `SetWindowLong(EXSTYLE \| 0x8)` | ❌ **不稳** —— OR 进去后读回又没了 |

### ⭐ 最要紧的一条：`.ps1` 的编码 —— 加 BOM 就能写中文

**PS 5.1 读 `.ps1` 的规则**（实测：两个文件同样内容，只差 BOM）：

```
UTF-8 带 BOM    → 只只        ✅ 正确
UTF-8 不带 BOM  → 鍙彧        ❌ 按 GBK 解码 → 乱码
```

| 结论 | 说明 |
|---|---|
| ✅ **`.ps1` 可以写中文** | 前提是**存成 UTF-8 with BOM**。旧说法「脚本一律纯 ASCII」过于保守 —— 那是**没有 BOM 时**的兜底 |
| ⚠️ 本项目的 Write / Edit 工具**不写 BOM** | 所以每次改完 `.ps1` 要**重新补 BOM**，否则下次运行中文全乱 |
| ✅ 补 BOM 的办法 | `[System.IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding($true)))` |

### 复核命令

```powershell
# BOM 是否为 EF BB BF
$p='tools\float-preview.ps1'; ([System.IO.File]::ReadAllBytes($p)[0..2] | ForEach-Object { '{0:X2}' -f $_ }) -join ' '
```

## 八、⭐ 系统状态采集能力与耗时实测（2026-10-15 —— probe 扩展 / M8 的直接依据）

> 全部在**本机**实跑（Win11 25H2 · i5-12450H · 32 GB · 单块 SATA SSD）。
> **用途**：回答「只只的 probe 能扩到哪」和「多久能采一次」。

### 8.1 能拿到什么

| 域 | ✅ 能拿到 | ❌ 拿不到 |
|---|---|---|
| **CPU** | 型号 · 物理核/逻辑核 · L1/L2/L3 · 当前/最大频率 · 总负载 · **每核负载（逐核）** | 核心温度 · 风扇转速 · 功耗 |
| **内存** | 总量/可用/使用率 · **每根条（插槽/容量/频率/厂商/料号）** | 实时带宽 |
| **磁盘** | 每分区容量/剩余/使用率/卷标/文件系统 · 物理盘型号/介质(SSD/HDD)/总线/健康 · 实时读写速率/队列/忙碌 | ⚠️ **这块 SATA SSD 的温度与磨损**（不上报 Storage 可靠性计数） |
| **GPU** | 型号 · 驱动版本/日期 · 分辨率/刷新率 · **引擎使用率（按引擎分）** | 温度 · 风扇 · 真实显存（集显「2 GB」是报的，实际吃共享内存） |
| **网络** | 网卡型号/速率/MAC · IP · 实时收发字节 · 错误包 · **TCP 连接数（按状态分组）** · 监听端口 | 每进程网络占用（要 ETW） |
| **进程** | 数量 · 线程总数 · 句柄总数 · 按内存/CPU 排序 · **单进程：路径 / 完整命令行 / 父进程 PID / 启动时间 / 工作集 / 数字签名** | 每进程磁盘与网络占用（要 ETW / 按实例计数器） |
| **温度** | ✅ **一个 ACPI 热区 ≈27.9 °C**（性能计数器，**不用管理员**） | 核心温度 · 每核温度 · 风扇 · 磁盘温度 |
| **系统 / 主板** | 主板型号 · BIOS 版本与日期 · 开机时长 · OS 版本/build · 服务数 · 计划任务数 · **自启项明细（Run 键）** | — |

### 8.2 ⚠️ 耗时表 —— 这张表决定 probe 能不能进 5 秒循环

| 方式 | 实测耗时 |
|---|---|
| **Node 原生 `os` / `fs.statfs`** | **微秒级** |
| `Win32_LogicalDisk` | 32 ms |
| `Win32_Process` | 274 ms |
| 性能计数器（CIM） | 372 ms |
| **起一次 PowerShell（全开销）** | **966 ms** |
| `Get-PhysicalDisk` | **1057 ms** |
| `typeperf`（起进程） | **1683 ms** |

**三条结论**：

1. **绝不能「一个指标起一次进程」** —— 起一次 PowerShell 就 ~1 s，5 秒采样循环会被直接打爆。必须**一次起、一次问完、批量解析**。
2. **指标必须分频**：高频（CPU/内存/磁盘容量 → Node 原生）· 中频（磁盘 I/O、网络、TCP → 一次进程问完所有计数器）· 低频（物理盘型号、进程清单、服务数 → 启动一次或每 N 分钟）。
3. **`typeperf` 可用**（exit 0，返回标准 PDH-CSV）—— 但要记住**它自己也要起进程**，不能一个指标一次。

### 8.3 ⚠️ 温度的两个坑

- **`Win32_TemperatureProbe` 是假阳性**：本机列出 4 个「数字传感器」，但 `CurrentReading` **全是空的** —— 类存在 ≠ 有值，**别用它**。
- **可用的是** `Win32_PerfFormattedData_Counters_ThermalZoneInformation`（`\_TZ.TZ00`，≈27.9 °C，**不需要管理员**）—— 但那是 **ACPI 热区（板温）**，**不是核心温度**。
- 想要核心温度/风扇：得上第三方（HWiNFO / LibreHardwareMonitor / smartctl）→ **与「零运行时依赖」冲突** → probe 应**可选降级**（有就拿、没有不报），**且别在告警文案里写核心温度**。

### 8.4 对只只的直接影响

- **M8-a（采集可控）**：档位 `off/slow/normal/fast` 与 `最小间隔 = max(实测耗时 × 20, 1000ms)` 的**依据就是 8.2 这张表**。
- **M8-b（安全哨兵）**：进程可拿到 **完整命令行 + 父进程 + 数字签名** → 「父进程是 `winword.exe` 却起 `powershell -enc …`」「路径在 `%TEMP%` 且签名非 Valid」都可判；但**全量签名校验慢**（抽查 40 个路径实测 5 个非 Valid），**必须低频跑**。

### 8.5 复核命令（复制即用）

```powershell
# CPU 与每核负载
Get-CimInstance Win32_PerfFormattedData_PerfOS_Processor | Select Name, PercentProcessorTime
# 内存条
Get-CimInstance Win32_PhysicalMemory | Select DeviceLocator, Capacity, Speed, Manufacturer
# 磁盘
Get-CimInstance Win32_LogicalDisk -Filter "DriveType=3"
Get-PhysicalDisk | Select FriendlyName, MediaType, BusType, HealthStatus
# 热区温度（唯一可用且免管理员）
Get-CimInstance Win32_PerfFormattedData_Counters_ThermalZoneInformation | Select Name, HighPrecisionTemperature
# 进程取证（命令行 + 父进程 + 签名）
Get-CimInstance Win32_Process -Filter "Name='explorer.exe'" | Select ProcessId, ParentProcessId, CommandLine
Get-AuthenticodeSignature (Get-Process explorer | Select -First 1 -Expand Path) | Select Status
# 耗时对比
Measure-Command { Get-CimInstance Win32_Process | Out-Null }
Measure-Command { Get-PhysicalDisk | Out-Null }
```

> ⚠️ 一句话：**能拿到的东西比想象多得多，但「代价」才是决定性的那张表。**

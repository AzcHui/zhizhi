### 🟠 2026-10-19（上午·托盘五项人手复验后）· **「回到右下角」回不到底边 —— 差 158 DIP**（1 缺陷，用户当场觉得"正常"）

> **用户实测五项全过、自述无问题。** 但我要日志时发现 `shell.json` 的数字对不上，追下去是真 bug —— 它**确实动了**（从屏幕顶部回到右下区域），只是**没贴到底边**，所以眼睛看着"回来了"。

**证据链（三个数字互相咬合，不靠猜）**

```
[09:19:10] 覆盖物方向 Y：常规（球贴窗底）      ← 锚从「翻转」翻回「常规」
[09:19:10] 托盘：回到右下角
[09:19:24] 内核 sidecar 已收掉                 ← Closing → SaveSettings()

%APPDATA%\zhizhi\shell.json  →  BallLeft: 1814, BallTop: 772
SystemParameters.WorkArea   →  1920 × 1032（探针实测）
```

**按公式该是多少**：`MoveToCorner()` 设 `Top = 1032 − 250 − 24 = 758`；常规锚下球顶 = `758 + (250 − 14 − 64) = 930`。
**实际存的是 772。差 158。**

**158 是哪来的**：`(Height − BallBottomMargin − BallSize) − BallTopMargin` = `(250 − 14 − 64) − 14` = `172 − 14` = **158** —— 正好是「球贴窗底」与「球贴窗顶」两种锚的偏移差。

**根因（顺序错了）**

```csharp
// homeItem 里的顺序
MoveToCorner();            // ← 按「窗口坐标」定位，隐含假设锚是"常规(球贴窗底)"
UpdateOverlayPlacement();  // ← 这里才把锚从"翻转"翻回"常规"，并保持「球屏幕位置不变」
SaveSettings();
```

1. `MoveToCorner()` 把窗口 `Top` 设成 758。**但此刻 `_ballTopAnchored == true`（球贴窗顶）**（用户 09:59 把球拖到屏幕上半部触发过翻转）→ 球的屏幕位置 = `758 + 14 = 772`
2. `UpdateOverlayPlacement()` 把锚翻回"常规"，按注释「翻转前后球屏幕位置不变」→ 球留在 **772**，窗口 `Top` 被反推成 `600`
3. → **球没回到该去的 930，而是停在 772，比底边高 158 DIP**

**X 方向同一个毛病**：`Left = 1920 − 320 − 24 = 1576`，若 `_ballLeftAnchored == true`（球贴窗左），球会停在 `1576 + 18 = 1594`，翻回右锚后 → 离屏幕右边 262 DIP。**本次没触发只是因为球没在屏幕最左。**

**为什么难发现**：位移是真的（从顶部回到右下区），只是**贴不到边**；而且只有「之前翻转过的用户」才踩（`_ballTopAnchored` 已被置过 true）。**首次启动不会中招**（初始是常规锚）—— 所以自验也过了。

**修法（最小改动）**：`MoveToCorner` 不要写「窗口坐标」，改写成**球的屏幕目标位置**，再交给已有的 `ClampForBall` 反推 —— 与拖动路径共用同一套换算：

```csharp
private void MoveToCorner()
{
    var wa = SystemParameters.WorkArea;
    var targetBallLeft = wa.Right  - 24 - BallSize;   // 球右缘距屏右 24
    var targetBallTop  = wa.Bottom - 24 - BallSize;   // 球下缘距屏底 24
    var win = ClampForBall(wa, targetBallLeft, targetBallTop);   // 按**当前锚**反推窗口
    Left = win.Left;
    Top  = win.Top;
}
```

**验收**：把球拖到屏幕**顶部**（触发 Y 翻转）→ 托盘「回到右下角」→ 读 `shell.json` 的 `BallTop` 应为 **930**（±2），球底距任务栏约 24 DIP。

| 🔴 **P0** | **拖动不跟手 ＋ 拖动途中反复闪烁**（用户实跑：球不跟鼠标走、拖动途中反复闪、松手就正常） | `e.GetPosition(this)` 返回的是**相对窗口**的坐标。窗口一移动，**上一帧存下的基准 `_dragLastMouse` 立刻作废** —— 它记的是「旧坐标系里的那个点」，窗口位移后同一个鼠标位置在新坐标系里已经不是那个值了。于是 `Left += p - lastP` 每次只补上「**鼠标位移 − 窗口已位移量**」 → 几何收敛 → **稳态速度 = 鼠标的一半**；而窗口自身移动会引发额外 `MouseMove`（WPF 重做命中测试），此时 `p` 因窗口位移反向变化 → `dx` 反号 → **窗口回退** → 再前进 → **原地来回跳 = 闪烁** | **把基准换成「屏幕 DIP 坐标」**：<br>`ScreenDip(e) = e.GetPosition(this) + (Left, Top)`<br>**并直接改回旧壳那种绝对式**（见下方「照抄对象」），每帧 `Left = 起点窗口X + (屏幕X − 起点屏幕X)`。<br>⚠️ **顺序陷阱**：`ScreenDip` 必须在 `Left +=` / `Left =` **之前**取（用移动前的 `Left`），否则两者不配套又错回去。<br>⚠️ `WindowStyle=None` 才成立（外框 = 内容区左上）；若将来加边框，要改用 `PointToScreen` ＋ DPI 换算 |

#### 📌 为什么开发方的「增量式」思路是对的，却还是错

他注释里写的判断**是对的**：「`GetPosition` 是相对窗口的，窗口一动参考系跟着动」。**但结论下错了一层** —— 他以为问题在「绝对式 vs 增量式」，于是改成增量式；而**真正的错因是「基准的坐标系」，不管绝对还是增量，只要基准是相对坐标就都是错的**。

**铁证：旧壳同一个功能是对的。** `tools/float-preview.ps1`：

```powershell
function Start-Drag([int]$cx, [int]$cy) {
  $script:dragOrigin = @{ CX = $cx; CY = $cy; WX = $form.Left; WY = $form.Top }   # ← cx/cy 是「屏幕」坐标
}
function Move-Drag([int]$cx, [int]$cy) {
  $x = $script:dragOrigin.WX + ($cx - $script:dragOrigin.CX)                      # ← 绝对式 + 屏幕坐标
  $form.Location = New-Object System.Drawing.Point($x, $y)
}
```

**旧壳用的正是「绝对式」** —— 它不振荡，因为 `$cx/$cy` 来自 WinForms 的**屏幕坐标**。WPF 移植时把坐标系换成了相对窗口，形式怎么改都救不回来。

> ⭐ **照抄对象**：把旧壳这三行搬到 C#，只把坐标换成屏幕 DIP：

```csharp
private Point _dragStartScreen;    // 按下瞬间：鼠标屏幕 DIP 坐标
private Point _dragStartWindow;    // 按下瞬间：窗口 Left/Top

private Point ScreenDip(MouseEventArgs e)
{
    var p = e.GetPosition(this);
    return new Point(p.X + Left, p.Y + Top);   // ⚠️ 必须在本帧移动窗口「之前」调用
}

// OnBallDragStart
_dragStartScreen = ScreenDip(e);
_dragStartWindow = new Point(Left, Top);

// OnBallDragMove
var s = ScreenDip(e);
if (!_dragMoved &&
    Math.Abs(s.X - _dragStartScreen.X) < DragThreshold &&
    Math.Abs(s.Y - _dragStartScreen.Y) < DragThreshold) return;
_dragMoved = true;
if (_panelOpen) CollapsePanel();
Left = _dragStartWindow.X + (s.X - _dragStartScreen.X);   // 绝对式：从起点定位，无累积误差
Top  = _dragStartWindow.Y + (s.Y - _dragStartScreen.Y);
```

**为什么绝对式比增量式更稳**：① 无累积误差 ② 窗口移动引发的额外 `MouseMove` 不会改变结果（`s` 恒定 → 位置恒定）③ 中途被别的逻辑改动 `Left` 也能自动纠正。

**修复方案已自证**：PART 2 的实测数据里 `p1 + Left1 = -300 + 300 = 0`、`p2 + Left2 = -400 + 400 = 0` —— **窗口怎么移，屏幕坐标恒定不变**，这正是可以当基准的量。

#### ⛔ 监工更正（2026-10-17 上午 · 观察③的建议有一处是错的）

我在观察③里写「把收尾抽成 `EndDrag()`，`LostMouseCapture` 也调它（**去掉其中的 `ReleaseMouseCapture`，避免重入**）」——**后半句错了。开发方照做后，用户实测「面板永久消失、无法退出」。**

**错在哪**：我把「避免重入」的解法选成了「不做那个操作」。但 `CaptureMouse()` 是**显式捕获**，它**不会因为鼠标松开就自动释放** —— 自动释放的只是 WPF 内部的**隐式**捕获（那是框架控件自己在 `MouseLeftButtonUp` 里调 `Release` 的）。一旦不显式 Release，捕获就被球**永久攥住**：所有鼠标事件只路由给球 → 悬停球不产生 `MouseEnter`（它本来就 `IsMouseOver`）、面板收不到任何事件 → **面板再也出不来**（面板里有「退出」按钮 → 表现为"无法退出"）。

**正解（开发方最终做法 ✅）**：**保留 Release，用幂等守卫解决重入** ——

```csharp
private void EndDrag() {
    if (!_dragging) return;                 // ← 幂等守卫：重复进来直接走
    _dragging = false;                      // ← 先清标志
    if (Mouse.Captured == _ball) _ball.ReleaseMouseCapture();   // ← 再释放（判空防被抢走）
    ...
}
```

`MouseUp → EndDrag → Release → 触发 LostMouseCapture → EndDrag` 再进时被守卫拦住 ⇒ 既释放了，也不重入。

> ⭐ **教训（第 10 条）**：**避免重入要用「幂等守卫」，不能用「省掉必要操作」。**
> 前者只是让重复调用失效，**后者会改变功能本身** —— 两者在代码里长得很像（都只是"加了/删了一行"），后果差一个数量级。
> **以后说「为了避免 X，去掉 Y」之前，必须先回答一句：Y 是不是这个功能活着的必要条件？**

### 2026-10-14 · M5 独立复验发现（监工；1 缺陷 + 2 观察）

**范围**：M5 台词池外置（commit `6a107df`）。**两条验收标准 + 四条硬约束全部独立复验通过**（见 M5 · F 节）；本小节只记**复验暴露的问题**。

| 级别 | 项 | 现象 / 证据（实测） | 建议出路 |
|---|---|---|---|
| 🟡 **缺陷**（低） | **纯数据台词包路径缺「id 冲突查重」** | `cli/loader.ts` 的**插件包路径**在第 3 步有查重（`registry.hasPlugin(manifest.id)` → `invalid`），但**纯数据路径 `loadPersonaJson()` 没有**，直接 `registry.adoptPersona(persona.id, …)`（`Map.set` = 静默覆盖）。实测：先注册 `probe-cpu`，再加载 `id:"probe-cpu"` 的 JSON → **未被拒绝**，`activeIds() = probe-cpu,probe-cpu`、`activeCount = 2`、`personaIds()` 里也多出 `probe-cpu` | **≈3 行修复**：在 `loadPersonaJson` 里 `definePersonaFromJson` 成功之后、`adoptPersona` 之前，加一句与插件路径同样的判：`if (registry.hasPlugin(persona.id)) → registry.reject(specifier, 'persona', 'invalid', 'id 冲突：…')`。<br>**与设计一致的理由**：`persona.json` 自己的说明写着「纯数据包 **没有** id 与 manifest 一致的约束」→ 用户复制内置 JSON 改台词时**很容易忘改 id**；一旦与别的插件重名，就会静默顶掉账面 |

| 🟢 观察 | **`meta` 键会覆盖内置占位符** | `plugin-sdk/define-persona.ts` 的 `fillPlaceholders`：先塞 `{type,severity,summary,key,value,unit}`，再 `for (meta) vars[k] = …` —— **meta 里的同名键会盖掉内置的**。当前探针的 meta 只有磁盘的 `{drive}`，无冲突；但 M7/M8 若给指标加 `meta.value` 之类，`{value}` 就会**静默变成别的数** | 低优先；改成「内置键优先」或对 meta 做键名前缀（如 `{meta.xxx}`） |

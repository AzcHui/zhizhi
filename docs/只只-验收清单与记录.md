**补充：M1 实施时会撞到的 2 个技术坑**（监工复核，提前说能省两小时）

| # | 坑 | 为什么会撞 | 怎么绕 |
|---|---|---|---|
| **A** | **pnpm `isolated` 链接下，未在 `package.json` 声明的包 `import()` 会直接失败** | M0 实测 `.modules.yaml` → `nodeLinker: isolated`：包只能访问**自己声明过**的依赖。若 cli 不声明 `@zhizhi/probe-cpu`，`import('@zhizhi/probe-cpu')` 会在 **catch 之前**就 `ERR_MODULE_NOT_FOUND` | 清单里的插件**仍要在 `cli/package.json` 保留依赖声明**；想表达"可缺失"就用 `optionalDependencies`。**验收测试操作的是「清单数组」（不是 package.json）**，所以"从清单去掉"能过 |
| **B** | **各插件的 `manifest.json` 当前没在 `exports` 里** | 三个插件的 `package.json` 只导出了 `"."`，所以 `import('@zhizhi/probe-cpu/manifest.json')` 会报 `ERR_PACKAGE_PATH_NOT_EXPORTED` | 各插件 `exports` 加一条 `"./manifest.json": "./manifest.json"`；或用 `import.meta.resolve()` 取入口路径再拼相对路径 |

> ℹ️ 另：M1 第 4 步把总线接通后，`bus` 在 M1 期内是「**在岗但无订阅者**」（`emit` 找不到 handler 只 return）—— 正常，真正的消费者（`rule` / `persona`）M2 / M5 才出现。

**结论：M0 通过。** 代码质量高于同类骨架，四条硬约束全守住。
M1 的最大风险（静态 import 过不了"删插件"验收）**已由用户在报表第三节的 M1 拆解中提前覆盖，方案正确**；只剩上面 2 个实施细节坑，提前知道即可。

**E · 前瞻风险**

| 🔴 **高** | **`sustained` 会"跨恢复期累计" → 误报** | 它靠「两次见到相隔 > `sustainMs` 才算新轮」来**间接推断**"中间恢复了"。**本轮已实测取证**（窗口压成 60s；序列=超标 0~30s → 恢复 35s → 65s 起再超标）：**`t=65s` 那次超标实际只持续 0 秒，却被放行报警** —— 恢复的 35s 被算进了"持续"。等价于**允许一次最长 2 分钟的中断**，而日常最常见的恰恰是「编译 40s → 停 50s → 再编译」—— **正是防毛刺要防的场景** | 判"新轮"的阈值不该用 `sustainMs`，应改成**采样间隔的 1~2 倍**（只容忍 1 个采样缺口）。需把 `intervalMs` 传进 `createGates`（≈5 行）；或由 cli 每 tick 主动清掉本轮未命中的 type。⚠️ **这个坑光看终端看不出来，要构造"超标—恢复—超标"序列才暴露** → ✅ **2026-10-14 已修**（见第三节） |

| 🟡 中 | **Scheduler tick 仍会重叠**（M0 已提，M2 未修） | `setInterval` + async handler 不等上一次完成。当前单 tick 仅 1.6~3.3ms，不紧迫；**M8 基线快照落盘后**单次一旦 >5s 就会并发打架 | M8 之前改自调度 `setTimeout`（≈5 行）→ ✅ **2026-10-14 已修**（见第三节） |
| 🟢 低 | `Dispatcher` 用 `find` 取首个匹配通道 | 若将来两个通道声明同一 severity，**后者永远不被调用、且不报错** —— 与"不静默吞错"原则相悖 | 命中多个时打 warn，或明确"一 severity 一 channel"并在加载期校验 |
| 🟢 低 | probe-cpu 首采样偏差（M0 已提） | 模块加载时取基准，加载与首采间隔大则数值偏低 | 可不管 |

**结论：M2 通过。** 三条验收标准**全部独立实测通过**，数据真实（真压满 12 核）、分通道正确、冷却期精确到毫秒。

**但必须挑明一条 🔴 高优先级缺陷**：**`sustained` 跨恢复期累计 → 会误报**，方向与"防毛刺"的初衷**相反**。
它在 M2 的终端演示里**看不出来**（要构造"超标—恢复—超标"序列才暴露），建议在 **M8（基线快照）动工之前**修掉 —— 那是"记忆"进场、判定逻辑会变复杂的时机。

**结论：技术前提全部通过；M3 是否完成，取决于用户对「位置 / 遮挡 / 按钮」的回答。**

**B · 端到端回归（真·压满 12 逻辑核）**

`--interval=800 --sustain-ms=3200 --cooldown-ms=4800 --ticks=14`：

- 尖峰 `0ms / 902ms / 1.8s / 2.7s` 全被 `sustained` 拦 → **不报** ✅
- ≈4.0s 放行第一条 → `{"type":"event","level":"warn",...,"cpu.usage 100%（阈值 >90）"}`

- **附带取证**：满载下 tick 从名义 800ms 抖到 **902ms**，**仍未被判新轮**（阈值 1600ms）→ 新阈值对抖动的容忍度在满载下也够用

**C · 复验中发现的新观察（下次动这块之前先看这两条）**

| 级别 | 观察 | 说明 |
|---|---|---|
| 🟢 低 | **阈值绑的是「名义间隔」，而实际间隔 = interval + handler 耗时** | 自调度后每次 tick 实际间隔 = `intervalMs + handler耗时`，但判新轮阈值取 `intervalMs × 2` → **安全条件 = handler 耗时 ≤ intervalMs**。当前 handler ≈3ms ≪ 5000ms，余量极大 ✅；但 **M8 基线快照落盘后，若单次耗时逼近采样间隔，持续判定会失效（永远判成新轮）** → 到那时要么阈值放宽到 `×3`，要么让 scheduler 回报**实测间隔**而不是名义值 |
| 🟢 低 | 容忍缺口 = 「1 个采样间隔」，语义上约等于「允许一段 ≈interval 的中断」 | 5s 采样 → 容忍 ~10s 中断，对 2 分钟窗口合理；但注意 **采样间隔越小、容忍的中断反而越短**（阈值随 interval 缩小）—— 调参时别误以为「采得越密越宽松」 |

> 📌 复盘：这次是**监工"只看日志看不出来"的缺陷被发现**的一个完整闭环 —— 缺陷由监工用事件序列取证 → 用户修复 → 监工再独立复验（还多测了 2 个边界）。
> **值得固化的做法**：**闸门这类"时间状态机"，验收要用「构造事件序列直接打」的方式，别只靠跑真实负载看日志** —— 真实负载只会喂出"持续超标"这一种序列。
